# TypeMatchup — SEO 精细化运营规则

目标：在不编造指标、不频繁重写页面的前提下，让 AI 运营的每次判断有可追溯证据、可复核的改动与明确的复盘结果。

## 1. 发现问题

1. 从 Google Search Console 官方数据读取**具体时间区间**的查询、页面、曝光、点击、CTR、平均排名。
2. 对查询词和页面做映射；多个相近查询词命中同一 URL 时，按实际页面去重。页面级数据与查询级数据必须分开。
3. 同时检查自然搜索排名和 SERP 意图。低 CTR 不自动代表标题差；平均排名 6–9 通常值得先比较搜索结果位置、内容意图和竞争页面。
4. 逐页核验当前 Title、Description、H1、首屏答案、计算器功能、canonical、内链以及移动端可用性。
5. 任何没有来源的数据都标记为“未取得”，不能估算填空。

## 2. 实验前登记

在 `experiments.csv` 新增一条实验记录，在 `decisions.md` 写清：
- 假设、目标查询词、目标 URL、GSC 时间窗与原始数值；
- 具体改什么、**不改什么**、为何是这个页面；
- 可参考的未修改页面 / 搜索词（如有），以及设备、国家、搜索类型筛选；
- 预期观察信号（如同口径点击和排名改善）及可能的负面信号；
- PR、部署时间、回退方式与负责人。

默认先做小批量、可回滚的实验；避免同时调整多个核心变量，更不能把所有页面一次性改动后声称效果可归因。

## 3. 安全执行与发布

- 通过 GitHub 分支和 Pull Request 记录修改，先过项目现有 TypeScript、SEO、生产构建、广告与 CMP 检查，再观察 Vercel 预览结果。
- 仅在相关检查通过、范围正确后合并。合并后确认正式部署 READY 与页面线上实际内容。
- 不擅自修改广告、分析脚本、环境变量、robots、sitemap、canonical 或申请编入索引。
- 技术验证通过，仅意味着“已上线”；SEO 状态仍标记 **⏳ 待观察**。

## 4. 效果评估

- 定期对比完整的连续七天 GSC 数据，但考虑索引和重新抓取滞后，**不足以判断时继续观察**；通常优先积累约 2–4 周的完整后续数据。
- 在相同页面、搜索词、国家、设备和搜索类型口径下核对变化，分别写出曝光、点击、CTR、平均排名；小样本或曝光大幅变化时谨慎解释。
- 对照相近但未修改页面的同期趋势（若具有可比性）；记录季节性、SERP 改动、竞争页面、新页面与搜索词结构变化。
- SEO 观察性数据通常无法像严格随机实验一样证明因果；避免写“由于本次修改必然提升”。
- 不把点击率的单点上升、部署 READY 或某次排名改善直接视为成功。

## 5. 状态决策

| 标记 | 什么时候使用 | 下一步 |
|---|---|---|
| ⏳ 待观察 | 新上线、数据不全、Google 尚未更新搜索摘要，或噪声太大 | 保留当前版本并继续取数 |
| ✅ 有证据支持保留 | 多个可比完整周期出现持续正向信号，且未观察到重大负效应 | 在决策日志写出完整数据、限制与保留理由 |
| ❌ 已撤回 | 页面错误、误导用户、数据事实错误或持续严重负面信号已核实 | 创建回退 PR，记录撤回理由和后续指标 |
| ⚪ 未执行 | 只有分析或建议，无可验证的代码提交和正式部署 | 不记作实验成功或已发布 |

**特别说明：** 下降不自动意味着需回滚；SEO 指标可能受外部环境影响。必须复查证据，保留人工审核空间。

## 6. 交付纪律

- 所有结论标明 GSC 报告名称、日期范围、页面、关键词和具体源 URL。
- 每次决策记录与对应的 GitHub PR / Vercel 部署关联。
- 仅报告已证实的数据；不得虚构受访人数、停留时长、跳出率、收益或优化效果。
- 每周复盘追加到 `weekly-reviews.md`，重大决策写到 `decisions.md`，状态同步到 `experiments.csv`。
